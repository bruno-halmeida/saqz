# Backend payment contract — final implementation — validated locally

All authenticated routes return `{value,requestId}` or `{error,requestId}`; no-store. UUID requestId required on every POST. Authenticated user is resolved from bearer; never accepted from request body. Monetary values integer BRL cents.

- GET `/api/receivables/groups/{groupId}?accountId=UUID`: value `{state:{accountId,groupId,enabled,pixEnabled,cardEnabled},permissions:{READ:{allowed,reason},CANCEL:{allowed,reason}}}`. Existing links readable after OFF/cutoff/group deletion/owner transfer by financial owner/current valid delegate. No fee or entitlement lookup. Missing link only visible when active group belongs to financial owner.
- POST `/api/receivables/charges/{chargeId}/preview`: `{requestId,accountId}`. value `{accountId,chargeId,groupId,payerId,dueDate,billingMonth,quotes,fingerprint}`. UUID chargeId references an existing manual charge. Requires financial authorization, current group ownership by financial account owner, eligibility/rollout/registration/enabled group, PENDING unreserved charge.
- POST `/api/receivables/charges/{chargeId}/approve`: `{requestId,accountId,fingerprint,accepted:true}`. value PaymentOrder `{id,accountId,chargeId,groupId,payerId,dueDate,status,quotes,fingerprint}`. Locks original charge, snapshots all configured methods/quotes, reserves against concurrent manual settlement/game cancellation. No silent enrollment of old debts.
- GET `/api/receivables/orders?after=UUID`: value `{orders:[PaymentOrder],nextCursor:UUID|null}`. Authenticated original payer only (no payer selector); includes terminal orders across groups after cutoff, membership exit and group soft deletion. Newest first by issued_at then id, descending, maximum 50 per page. Pass nextCursor as after. Unknown or another payer’s cursor yields an empty page; malformed UUID returns 400. Local read only, no provider/financial side effects.
- GET `/api/receivables/orders/{orderId}`: value `{order:PaymentOrder,instruments:[PaymentInstrument]}`. Financial owner/current delegate or original payer; payer need not remain member. No new-business gate.
- POST `/api/receivables/orders/{orderId}/instruments`: `{requestId,method:"PIX"|"CARD",fingerprint,accepted:true,payer:{name,cpfCnpj}}`. `fingerprint` is approved order fingerprint. All input including name/document participates in idempotency digest; payer data encrypted. Name/document required for customer creation, never guessed from profile. Same existing customer cannot silently change legal data. Original payer only; configured snapshot method only; at most one live instrument. value PaymentInstrument `{id,accountId,orderId,quote,status,paymentId,checkoutId,pixPayload,pixImage,checkoutUrl,confirmed,settled,available,splitSettled,expiresAt}`. `checkoutUrl` carries hosted Asaas **invoiceUrl**, not /checkouts. No PAN/CVV. UNKNOWN/CREATING mean pending recovery, not permission to create another instrument.
- POST `/api/receivables/orders/{orderId}/reconcile`: `{requestId}`. Authorized reader. Queries provider by stored payment ID or exact externalReference; value order detail.
- POST `/api/receivables/orders/{orderId}/cancel`: `{requestId}`. Financial owner/current financial delegate only. Existing order maintenance independent of rollout/plan. CANCEL_PENDING retains reservation until remote cancellation evidence; value order detail. No requested refunds.
- POST `/api/receivables/webhooks/asaas/{accountId}`: anonymous with required account-specific `asaas-access-token`; raw Asaas JSON. 200 only after encrypted durable insertion, 401 wrong token/account, 400 malformed. Dedup `(accountId,event.id)`. Payload is a wake-up; processor queries authenticated account provider state before financial application. Browser redirect has no financial effect.

FeeQuote fields: feeScheduleId,termsVersion,method,baseCents,feesCents,totalCents,expectedNetCents,commissionCents,providerFeeCents. Saqz split uses payment.split[].fixedValue as BRL decimal, never percentage.

HTTP errors: INVALID_INPUT 400; NOT_FOUND/UNAUTHORIZED 404; CONFLICT 409; missing conditions/provider 503; commercial denial 403. A pending created instrument returns 200 with UNKNOWN/CREATING state.

Provider decision: POST /payments with PIX or CREDIT_CARD only, no UNDEFINED/installments. CARD redirects invoiceUrl; Pix fetches /payments/{id}/pixQrCode. Customer creation has a separate durable pre-call UNKNOWN fence. Payment creation has durable operation lease and externalReference equal instrument UUID. Uncertain calls are queried, never recreated. An absent eventually consistent list does not prove rejection. Remote checkout lookup/idempotency was not assumed; /checkouts is outside this implementation.

Operational deployment remains OFF by default (`saqz.receivables.payments-enabled` must be explicitly true). Deployment encryption credentials, subaccount key, platform wallet and public webhook base URL/email must be configured; the financial owner then POSTs the webhook setup endpoint (no secret SQL seed); no real provider calls were authorized or made in this work. Existing financial configuration still controls new business separately.

## Operational webhook setup

POST `/api/receivables/accounts/{accountId}/webhook` with `{requestId}`. Financial owner only, refreshed on every call, maintenance independent of commercial gate. Returns value `CONFIGURED` or `RESULT_PENDING`; token is never returned. Server creates 48 random bytes and commits encrypted token before provider POST /webhooks; timeout replays GET /webhooks matching URL and token-derived unique name (and hasAuthToken/enabled), never a second POST. New business requires webhook state configured. Required deployment properties: saqz.receivables.webhook-base-url (HTTPS application origin), saqz.receivables.webhook-email; existing saqz.receivables.asaas-base-url and platform-wallet-id. Route is subject to the existing bounded anonymous webhook body filter (64 KiB).

Additional statuses: DISPUTED and RECOVERY_PENDING are nonterminal account facts for chargeback requested/dispute and won dispute awaiting provider settlement. They remain polled. Official subsequent CONFIRMED/RECEIVED recovers the existing receipt without duplicate cash; REFUNDED is the actual terminal reversal. Provider fee and commission movement entries require observed values; commission requires split DONE. Refund split credits require refundedSplits.done/value. Unknown reversal provider costs and missing returned split facts generate explicit operational occurrences rather than invented cost values.

Customer HTTP 400 with structured provider errors is definitive rejection: no payment is created, instrument closes, and a new request can submit corrected encrypted payer data. Lost response and absent eventual-consistency queries remain UNKNOWN. `payments-enabled` is a deployment composition switch: once live orders exist, do not turn it off to pause sales; use administrative rollout OFF/group deactivate, which preserve maintenance/webhooks/recovery.

Setup webhook400 estruturado: retorna503 CONFIGURATION_UNAVAILABLE e preserva estado REJECTED; nova tentativa após corrigir configuração pode enviar POST porque há prova de rejeição anterior. Timeout continua RESULT_PENDING/UNKNOWN com recuperação somente por consulta. Sem renovação automática de Pix expirado; conferir chave Pix da subconta antes de homologação.

## Historical milestones

`confirmed`, `settled`, `available` and `splitSettled` record milestones already observed and are monotonic. They are not current balance or permission to withdraw. A refund or dispute can retain those flags; consumers must present the current `status` and must not derive wallet availability from these booleans. Wallet balance and withdrawals are outside this contract.
